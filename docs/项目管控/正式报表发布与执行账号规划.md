# 正式报表：版本、审批与执行账号

> 状态：单级审批第一版已实现；执行边界及验收见[正式报表发布与执行账号验收](../开发指南/正式报表发布与执行账号验收.md)。
> 日期：2026-10-18。
> 下文保留设计与验收目标；本轮实现包括版本、单级审批、正式发布和专用执行账号，不代表后续多级工作流或平台行级权限已交付。

## 1. 产品模型

报表提供个人开发和正式发布两种使用方式：

- 个人开发使用开发者自己的数据库连接，继续执行现有的数据源授权、只读和个人凭据隔离规则。
- 正式报表由管理员审核版本、选择专用报表执行账号、确认共享受众并批准，再显式发布。查看者凭报表访问权限运行已发布版本，无须配置个人数据库账号。
- 既有“登录后共享”继续表示共享定义、各人使用自己的连接；它不等于经过审批的正式发布，也不能自动切换到专用账号。

“报表执行账号”指平台托管的数据库服务账号。它不是普通平台登录用户，不使用作者或管理员的个人连接充当正式运行依赖。第一版默认仅接受支持强制只读执行的连接器和数据库账号。

正式报表的查看权限可以授予没有直接数据源使用权限的业务用户。该授权只允许调用特定报表的已批准查询，不能获得数据源目录、工作台查询、数据库元数据或账号使用权限。这是独立、显式批准的数据访问通道。

## 2. 开发、审批和发布流程

1. 用户 A 使用个人连接开发、预览和保存草稿。
2. 提交审批时，从草稿生成不可修改的内容版本，例如 v1；后续修改进入新草稿，不覆盖提交内容。
3. 管理员审阅 SQL、数据源修订、数据库、图表配置和共享受众，选择已获准用于该数据源的报表执行账号。
4. 管理员在受控审核接口中，使用选定账号对冻结的查询进行只读验证。确认账号实际可访问的数据适合目标受众后批准。
5. 批准记录固定“内容版本 + 执行账号配置修订 + 受众范围 + 执行策略”的完整摘要。账号选择在批准前完成，批准后不能另换账号直接发布。
6. 管理员显式发布该批准记录，事务性更新当前发布指针。发布和批准分开记录，第一版允许同一管理员完成这两个操作。
7. 普通用户仅能查看当前已发布版本。开发者继续开发 v2，v1 在 v2 获批并发布前保持可用。

第一版采用单级管理员审批，提交者不能批准自己的版本。退回填写原因；内容修改后生成新版本并重新提交。草稿和待审批版本不进入正式报表列表。

内容审批状态与发布状态分开管理：

| 对象 | 状态与含义 |
| --- | --- |
| 草稿 | 可编辑，使用乐观锁防止覆盖；不是正式版本 |
| 内容版本 | 提交时生成不可变快照；退回后保留审阅记录 |
| 审批申请 | 待审、批准、退回、撤回；批准绑定完整执行与授权快照 |
| 发布记录 | 发布、回滚、下线事件；报表另存当前生效发布编号 |

已批准内容版本可以作为回滚候选，但回滚前必须重新检查原执行账号、受众授权和数据源状态仍有效。回滚产生新发布事件，不改写历史版本。定义版本不等于结果快照；运行时仍读取当时的数据库数据。

## 3. 版本与批准边界

提交后固定 SQL、数据库、数据源不可变修订、图表配置及未来的参数定义。管理员选择执行账号和受众后，生成不可变的批准清单；审批记录引用该清单并存储摘要。执行账号密码不进入清单、摘要、版本内容或审批响应。

以下变化需要新的批准清单和重新审批：

- 查询或展示定义变化，包括 SQL、数据库、图表字段映射、参数定义。
- 更换数据源修订、执行账号数据库身份、目标地址、驱动或代理路径。
- 更换共享用户、用户组或扩大账号的受管使用范围。
- 放宽执行限制或其他影响查询、授权的策略。

仅轮换同一数据库身份的密码，走独立的管理员凭据维护和连接验证流程，不要求重新审批每份报表。停用账号或收紧系统策略立即生效，不能通过历史批准绕过。

一个报表采用一个当前发布指针。发布、回滚和下线使用事务及预期发布编号比较，防止两名管理员同时操作导致覆盖。执行请求绑定明确的发布编号；排队期间发布发生变化时要求重新加载，不能悄悄切到另一版本。

## 4. 报表执行账号

账号按数据源和业务权限范围配置，可以供多份获准报表使用，不要求每张报表单独创建一个数据库用户。

建议保存以下信息：

- 显示名称、责任人、状态、数据源修订及目标数据库。
- 数据库身份、只读能力、准许使用范围、配置修订及最近验证结果。
- 加密的认证材料；接口仅返回“已配置”等状态，不能读取明文密码。
- 凭据轮换记录和引用该账号的报表清单，支持停用前评估影响。

账号仅授权给专用报表执行路径，不能作为普通个人连接出现在数据工作台，也不能允许客户端提交任意 SQL 借用账号执行。账号管理与凭据读取必须使用独立的后端授权逻辑，不能通过把当前操作者替换为账号所有者来复用个人连接权限。

数据库端仅授予需要的表或视图读取权限；服务端继续使用 AST 检查、数据库只读事务、超时、行数限制和并发队列。只读事务不能替代数据读取范围控制。

统一执行账号意味着数据库看到相同的身份，查看者原有个人数据库行级权限不会自动继承。第一版优先采用限定数据范围的数据库视图和业务账号；同一批准版本的受众应被允许访问该账号通过此查询返回的数据。跨部门、跨企业隔离不能依靠浏览器筛选。基于当前登录身份的服务端行级策略属于后续独立能力。

## 5. 正式报表权限与生命周期

正式报表使用独立的查看授权，可指定用户和用户组。查看、开发、审核、发布和账号管理是不同能力；第一版可由现有开发者和管理员角色承载，普通查看者不获得编辑或执行账号管理权限。

正式查看接口仅返回展示所需信息，不默认公开 SQL、账号用户名、连接地址、审批内部说明或凭据。查询定义及版本比较向有开发或审核权限的用户开放。

发布后的报表、版本及执行账号由平台受管资源持有，不依赖作者的个人连接。移除作者个人连接或停用作者不影响已发布报表。删除作者前必须处理责任人移交；不能沿用当前报表对作者删除级联的行为。历史操作人允许保留显示快照，审计记录不得因用户删除丢失。

账号停用、数据源禁用、用户停用、撤销报表查看权限和下线报表，都要阻断后续执行。用户组成员资格在请求时检查；分组成员维护需要授权和审计，它会影响以该组为受众的报表。

当前实例没有因“个人/共享”自动形成企业租户边界。本方案第一版按单实例的管理范围实施；未来多组织运营时，账号、审批、版本和授权均必须带明确组织边界，不能跨租户解析引用。

## 6. 执行、并发与审计

正式执行由服务端解析“报表 → 当前发布 → 批准清单 → 内容版本与执行账号”。客户端只提交报表标识、预期发布编号、执行 UUID，以及未来经声明和验证的参数，不接收 SQL、连接或账号覆盖值。

保留既有报表执行的只读检查、数据库只读事务、精度保真、截断提示、队列、超时和持久执行编号。新增以下边界：

- 创建草稿、提交、审批和发布采用幂等编号；相同编号不同内容拒绝处理。
- 版本、审批决定及发布事件追加保存；批准、退回等互斥操作通过条件更新保证只有一个成功。
- 执行指纹包含操作者、发布编号和批准清单摘要，不能跨人或跨版本复用执行编号。
- 入队和真正发出 SQL 前重新检查用户、报表授权、当前发布、数据源、账号及策略；撤权后的排队请求不能启动。
- 查询结束、发送结果前再次检查授权。已启动查询尽力取消；已交付的数据无法追溯收回。
- 账号验证失败直接报错，不回退到管理员、作者或查看者的其他账号。
- 第一版不增加结果缓存；后续缓存必须覆盖执行身份、授权范围、版本及参数，不能只按报表 ID 复用。

操作审计同时记录实际访问用户、作者、审批者、发布者、报表 ID、内容版本、批准记录、发布编号、实际数据库账号、数据源修订、执行 UUID 和结果状态。继续使用现有可靠写入机制，不在操作审计中保存凭据、SQL 正文或查询结果。

## 7. 存储与接口改造范围

计划新增以下逻辑实体，最终表名以实施迁移为准：

| 实体 | 职责 |
| --- | --- |
| 报表主记录 | 稳定标识、受管责任人、个人/正式模式、当前发布指针 |
| 工作草稿 | 可编辑定义及乐观锁版本 |
| 内容版本 | 不可变的 SQL、数据源修订、图表及参数快照 |
| 执行账号及配置修订 | 受管身份、加密凭据、目标与适用范围、启停状态 |
| 审批申请与批准清单 | 申请状态、固定的内容/账号/受众绑定、摘要、决定及意见 |
| 发布事件 | 发布、回滚、下线、操作者、时间及前后发布编号 |
| 正式报表授权 | 批准范围内的用户和用户组查看授权 |

现有 `sys_reports.version` 是并发修改版本号，不能用来声称已经实现历史版本管理。新模型应保留个人报表接口兼容性，新增版本、送审、审核、发布、下线、回滚和执行账号管理接口，并提供正式报表专用的授权与执行入口。

既有个人和共享报表不自动转为已审批或已发布状态，不自动复用作者凭据。作者可从已有定义创建正式报表草稿，走完整送审流程。身份迁移与现有执行编号的指纹格式应分别处理，避免破坏个人执行重试语义。

前端保持数据工作台简洁。在报表模块增加“我的开发”“已发布”范围；管理员增加待审列表及执行账号管理。编辑界面区分草稿和已发布版本，展示版本差异、审批意见、当前运行版本及账号状态；普通查看页不显示开发控件。

## 8. 第一版实施与验收

第一版实现单级审批、不可变内容版本、受管只读账号、用户/分组查看授权、显式发布、下线、回滚和完整审计。不引入通用工作流引擎、多级会签、复杂行级策略、定时订阅、匿名访问或结果缓存。

验收必须覆盖以下实际场景：

1. A 使用个人账号开发，管理员以受管只读账号审批验证；A 不得审批自己的申请。
2. 没有个人数据库连接但获准查看的 B 能运行已发布版本；没有报表授权的 C 不能查看或执行。
3. B 不能读取 SQL/凭据，不能修改请求借用报表账号运行任意 SQL，也不能通过工作台调用该账号。
4. 提交后修改草稿不改变送审内容；批准后改变 SQL、执行账号或受众必须重新审批。
5. v1 正常服务期间开发和退回 v2，不影响 v1；批准发布 v2 后再执行 v1 请求返回版本冲突。
6. 并发提交、重复审批、重复发布、发布与下线竞争都有确定结果，不能产生多份当前发布或重复操作。
7. 账号停用、源禁用、用户停用、组成员移除和权限撤销阻断新请求、排队请求及未交付结果。
8. 作者移除连接、离职停用不影响已发布版本；作者删除要求责任人移交且保留版本与审计。
9. 密码轮换后使用同一数据库身份执行；错误凭据不回退到个人账号。更换数据库身份需要新的批准。
10. 回滚只允许选择仍满足账号、数据源和授权条件的批准记录，产生新的发布事件并保留历史。
11. 数据库隐藏写入仍被只读事务拒绝；截断、数值精度及实际数据库身份有真实数据库验收。
12. 服务重启、审计写入失败和网络超时重试遵守既有可靠写入及幂等约束；审批记录和发布指针不能处于半完成状态。
