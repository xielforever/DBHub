# 部署运维指南

仓库根 `docker-compose.yaml` 和 `scripts/cloud/compose.yaml` 用于开发。生产使用 [docker-compose.prod.yaml](../../docker-compose.prod.yaml)，运行已构建的 Go、Nginx 镜像，连接外部 PostgreSQL 与 Redis，不挂载源码、不启动 Vite 或 Air。

## 1. 生产运行方式

浏览器通过 HTTPS 网关访问前端 Nginx；静态资源及 SPA 路由由前端提供，同源 `/api/` 转发至后端。后端不发布宿主端口，前端默认绑定 `127.0.0.1:8088`，由外部 HTTPS 网关转发。需要其他绑定时设置 `FRONTEND_BIND_ADDRESS`、`FRONTEND_HTTP_PORT`。

| 组件 | 构建/运行方式 |
| --- | --- |
| 前端 | Node 24.12.0 slim 按 `package-lock.json` 执行 `npm ci`、类型检查和 Vite 构建；Nginx 1.30.6 提供静态资源 |
| 后端 | Go 1.25.5 Bookworm，`CGO_ENABLED=1`，使用 vendor 中的 PG/MySQL AST 解析器；Debian Bookworm slim 以 UID 65532 运行 |
| 元数据库 | 外部 PostgreSQL，存储用户、连接、权限、历史及执行回执；启动时自动执行内嵌迁移 |
| Redis | 外部认证会话、撤销与在线状态服务；业务表和 SQL 结果不进入缓存 |

基础镜像均固定摘要。前端从容器 DNS 动态解析 `backend`，API 代理等待上限 180 秒，覆盖 30 秒排队、最多 120 秒执行及清理。客户端取消会传至后端；代理不自动重放写请求。`/assets/` 缺失文件返回 404，带哈希的静态资源可长期缓存，HTML 要求重新验证。

容器 HEALTHCHECK 分别验证前端 `/healthz` 和后端 `/api/health`；它们是 HTTP 存活检查，不能代替数据库查询、认证会话和功能验收。后端检查不需要 shell、curl 或凭据；前端本机检查不走外部 HTTP 代理。

## 2. 构建镜像

所有构建在 Docker 中进行。后端解析器需要 CGO，不能改为 `CGO_ENABLED=0` 或直接换成不兼容的 Alpine 运行时。

```sh
docker build -t dbhub-backend:phase1-release -f backend/Dockerfile backend
docker build --secret id=proxy_ca,src="${CODEX_PROXY_CERT:-/etc/ssl/certs/ca-certificates.crt}" -t dbhub-frontend:phase1-release -f frontend/Dockerfile frontend
```

Cloud 中沿用会话代理和 CA，不关闭 TLS 或 npm 完整性校验。普通网络下 `proxy_ca` 挂载可省略。前端依赖安装失败会中止构建，不回退到会改写锁文件的 `npm install`。构建依赖与会话证书不会进入运行镜像。

发布前为通过验收的镜像设置不可变版本标签、推送至团队镜像仓库，并记录其摘要和源码提交。生产配置中的 `DBHUB_BACKEND_IMAGE`、`DBHUB_FRONTEND_IMAGE` 指向该版本或摘要，不依赖可变的 `latest`。

## 3. 配置与启动

将运行配置保存在受控的密钥管理系统或权限 0600 的环境文件，例如 `/secure/dbhub.production.env`。不要使用 Cloud 自动生成的开发凭据，不要输出展开后的 Compose 配置。

| 变量 | 要求 |
| --- | --- |
| `DBHUB_BACKEND_IMAGE` / `DBHUB_FRONTEND_IMAGE` | 必填，已验证的镜像标签或摘要 |
| `APP_SECRET_KEY` | 必填，至少 32 字节，JWT 与连接凭据加密共用；跨重启及恢复保持一致 |
| `APP_ADMIN_USERNAME` / `APP_ADMIN_PASSWORD` | 管理员名默认 admin，密码必填且禁止 admin123；后端只在用户不存在时引导创建，后续改密使用账号接口 |
| `DATABASE_URL` | 必填，生产元数据库连接；使用服务端证书验证，例如 `sslmode=verify-full` |
| `REDIS_URL` | 必填，生产认证会话服务；跨网络使用受保护连接，例如 `rediss://` |
| `META_DB_MAX_CONNS` | 默认 10，按实测容量配置 |
| `GOMAXPROCS` | 默认 4，不等同于容器 CPU 硬限额 |
| `JWT_ACCESS_TTL_MINUTES` / `JWT_REFRESH_TTL_HOURS` | 默认 15 分钟 / 168 小时 |
| `CORS_ALLOWED_ORIGINS` | 同源部署可留空；有跨域客户端时填写实际 HTTPS Origin，逗号分隔 |
| `DBHUB_AI_BASE_URL` / `DBHUB_AI_MODEL` / `DBHUB_AI_API_KEY` | 可选；模型稍后配置，不影响基础 SQL 工作台 |

```sh
docker compose --env-file /secure/dbhub.production.env -f docker-compose.prod.yaml config --quiet
docker compose --env-file /secure/dbhub.production.env -f docker-compose.prod.yaml up -d --wait --wait-timeout 120
docker compose --env-file /secure/dbhub.production.env -f docker-compose.prod.yaml ps
```

前端等待后端健康后启动。再通过实际 HTTPS 域名检查登录、真实 SELECT、权限与执行回执；检查管理员指标 `GET /api/v1/metrics/query`，确认回执存储可读。监控配置见 [SQL 工作台运行指标](../开发指南/SQL工作台运行指标与压测.md)。

## 4. 迁移与备份

后端在监听 HTTP 前执行 `internal/db/migrations`，通过 `schema_migrations` 记录版本，同版本重启不重复执行。当前含 0001–0019；0017–0019 分别增加持久化执行登记、目标数据库名及指标索引。首次迁移和索引建立时间受现有数据规模影响，应在发布前对脱敏副本验证。

升级前记录旧镜像摘要、配置版本与迁移版本，停止发起新的 SQL，等待活动任务排空，并对元数据库做一致性备份。示例使用运维端已配置的 libpq service 和受控凭据文件，避免在命令参数中写入密码：

```sh
umask 077
pg_dump --dbname=service=dbhub_meta_backup --format=custom --file=/secure/backups/dbhub-meta.dump
pg_restore --dbname=service=dbhub_meta_restore_check --exit-on-error /secure/backups/dbhub-meta.dump
```

这些运维客户端也可运行在 PostgreSQL 工具容器中。恢复检查必须指向独立空库，验证迁移版本、用户、加密连接和回执数据。密钥管理系统要保留与备份对应的 `APP_SECRET_KEY`；数据库备份不包含该密钥，也不包含外部目标业务库的数据。Redis 需要按会话保留策略备份；恢复元数据库不能恢复已经丢失的 Redis 登录会话。

## 5. 回滚步骤与边界

1. 停止新 SQL 请求并排空任务，保留旧镜像摘要、配置和备份。
2. 当前数据库结构与旧应用兼容时，将两个镜像变量改回之前通过验收的摘要，重新执行 `up -d --wait`，再验证登录、读取和回执。不要自动执行反向 DDL。
3. 结构不兼容时，停止写入，在维护窗口将升级前备份恢复到独立数据库，使用对应应用密钥、连接配置与兼容镜像切换。核对升级后的新增元数据，不能直接覆盖仍在使用的数据库。
4. 后端重启会关闭目标连接、回滚未提交的活动事务；已自动提交的业务写入不会因应用回滚而撤销。取消、断网或进程终止后的 unknown 回执须核实目标数据库，不能自动重跑。

当前已验证生产后端替换、会话与执行编号持久性、元数据库备份恢复；尚未验证某个历史生产版本的应用降级。准备发布时需要指定实际回滚版本，在数据副本上验证兼容性。

## 6. Cloud 内复现生产镜像验收

```sh
# 先按第 2 节构建两个镜像
./scripts/cloud/release.sh up -d --wait --wait-timeout 180
./scripts/cloud/release.sh run --rm --no-deps browser

# 在后端替换前后验证持久化回执和同编号防重
./scripts/cloud/release.sh run --rm --no-deps ops node /app/scripts/cloud/release_operational_test.mjs prepare
./scripts/cloud/release.sh up -d --no-deps --force-recreate --wait backend
./scripts/cloud/release.sh run --rm --no-deps ops node /app/scripts/cloud/release_operational_test.mjs verify

# 验收结束后停掉独立项目；不停止开发项目，也不删除数据
./scripts/cloud/release.sh stop
```

该 wrapper 合并生产编排与 `scripts/cloud/release.compose.yaml`，使用独立项目 `dbhub-release-check`、私有状态目录 `/workspace/dbhub-release-check`，随机创建仅用于本地测试的凭据。验收数据库文件放在 `${DBHUB_BUILD_ROOT:-/tmp/dbhub-cloud-build}/release-data`，节省 Cloud 持久盘；该临时路径不用于生产持久化，环境重建后可能丢失。

`browser` 和 `ops` 仅在显式运行时启动。浏览器依赖在临时 Debian 容器安装，截图与 JSON 留在私有状态目录。`ops prepare` 暂存一个权限 0600 的会话/请求状态文件，成功核实后撤销会话并删除状态文件；未核实前不要覆盖该文件。浏览器使用本地 `dbhub_cloud_demo` 合成数据，不连接生产数据源。

完整结果与剩余边界见 [第一阶段生产构建验收](../开发指南/第一阶段生产构建验收.md)。此前短时容量结果见 [单实例容量基线](../benchmarks/SQL工作台容量基线-2026-10-16.md)；真实业务 SQL 的 30 分钟混合负载仍需业务数据副本。
