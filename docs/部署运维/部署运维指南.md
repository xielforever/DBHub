# 部署运维指南

支持 Docker Compose、独立 Docker CLI、Helm/Kubernetes、源码/systemd 四种方式，统一配置、安装入口与差异见[部署方式](../../deploy/README.md)。以下生产安全、升级、备份和回退要求适用于四种方式。当前支持单后端实例：普通工作台队列与活动事务仍属单进程，Helm限制单副本并使用Recreate；报表共享租约不代表完整多实例运行已验收。

仓库根 `docker-compose.yaml` 和 `scripts/cloud/compose.yaml` 用于开发。生产使用 [docker-compose.prod.yaml](../../docker-compose.prod.yaml)，运行已构建的 Go、Nginx 镜像，连接外部 PostgreSQL 与 Redis，不挂载源码、不启动 Vite 或 Air。

## 1. 生产运行方式

浏览器通过 HTTPS 网关访问前端 Nginx；静态资源及 SPA 路由由前端提供，同源 `/api/` 转发至后端。后端不发布宿主端口，前端默认绑定 `127.0.0.1:8088`，由外部 HTTPS 网关转发。需要其他绑定时设置 `FRONTEND_BIND_ADDRESS`、`FRONTEND_HTTP_PORT`。

| 组件 | 构建/运行方式 |
| --- | --- |
| 前端 | 按[frontend/Dockerfile](../../frontend/Dockerfile)的Node镜像及 `package-lock.json` 执行 `npm ci`、类型检查和 Vite 构建；同一Dockerfile指定的Nginx提供静态资源 |
| 后端 | 按[backend/Dockerfile](../../backend/Dockerfile)和go.mod的Go镜像构建，`CGO_ENABLED=1`，使用 vendor 中的 PG/MySQL AST 解析器；Debian Bookworm slim 以 UID 65532 运行 |
| 元数据库 | 与当前迁移及部署配置相容的外部PostgreSQL，存储用户、连接、权限、历史及执行回执；启动时自动执行内嵌迁移。业务数据源的版本范围单独验证 |
| Redis | 外部认证会话、撤销与在线状态服务；业务表和 SQL 结果不进入缓存 |

基础镜像均固定摘要。前端从容器 DNS 动态解析 `backend`，API 代理等待上限 180 秒，覆盖 30 秒排队、最多 120 秒执行及清理。客户端取消会传至后端；代理不自动重放写请求。`/assets/` 缺失文件返回 404，带哈希的静态资源可长期缓存，HTML 要求重新验证。

容器 HEALTHCHECK 分别验证前端 `/healthz` 和后端 `/api/ready`；后者在 2 秒上下文内检查元数据库所有者/受限运行连接、Redis 和本地审计容量，关键依赖故障返回 503。`/api/health` 保留进程存活检查。后端检查不需要 shell、curl 或凭据；前端本机检查不走外部 HTTP 代理。探针结果还需结合登录、真实数据查询与告警送达验收。

后端请求头限制 16 KiB，读取请求体上限 15 秒，响应期限 180 秒以覆盖查询排队和执行。Nginx 提供严格脚本 CSP、禁止嵌入、MIME 嗅探保护、Referrer/Permissions Policy 和 HSTS；HTML、静态资源及错误响应均保留安全头。HTTPS 网关负责证书和 HTTP 重定向。CSP 允许组件必要的内联样式及 Monaco 的同源/Blob Worker，脚本限同源。API 设置 `no-store`；认证会话暂时不可用返回 503，前端保留令牌供稍后重试。

## 2. 构建镜像

所有构建在 Docker 中进行。后端解析器需要 CGO，不能改为 `CGO_ENABLED=0` 或直接换成不兼容的 Alpine 运行时。

```sh
docker build -t dbhub-backend:local-candidate -f backend/Dockerfile backend
docker build --secret id=proxy_ca,src="${CODEX_PROXY_CERT:-/etc/ssl/certs/ca-certificates.crt}" -t dbhub-frontend:local-candidate -f frontend/Dockerfile frontend
```

按实际环境使用代理和CA，不关闭TLS或npm完整性校验。普通网络下 `proxy_ca` 挂载可省略。前端依赖安装失败会中止构建，不回退到会改写锁文件的 `npm install`。构建依赖与会话证书不会进入运行镜像。

发布前为通过验收的镜像设置不可变版本标签、推送至团队镜像仓库，并记录其摘要和源码提交。生产配置中的 `DBHUB_BACKEND_IMAGE`、`DBHUB_FRONTEND_IMAGE` 指向该版本或摘要，不依赖可变的 `latest`。

## 3. 配置与启动

将运行配置保存在受控的密钥管理系统或权限 0600 的环境文件，例如 `/secure/dbhub.production.env`。不要使用自动生成的开发凭据，不要输出展开后的 Compose 配置。

| 变量 | 要求 |
| --- | --- |
| `DBHUB_BACKEND_IMAGE` / `DBHUB_FRONTEND_IMAGE` | 必填，已验证的镜像标签或摘要 |
| `APP_SECRET_KEY` | 必填，至少 32 字节，JWT 与连接凭据加密共用；跨重启及恢复保持一致 |
| `APP_ADMIN_USERNAME` / `APP_ADMIN_PASSWORD` | 管理员名默认 admin，密码必填且禁止 admin123；后端只在用户不存在时引导创建，后续改密使用账号接口 |
| `DATABASE_URL` | 必填，生产元数据库连接；使用服务端证书验证，例如 `sslmode=verify-full` |
| `REDIS_URL` | 必填，生产认证会话服务；跨网络使用受保护连接，例如 `rediss://` |
| `DBHUB_NACOS_ENABLED` / `DBHUB_NACOS_SERVER_ADDR` / `DBHUB_NACOS_NAMESPACE` / `DBHUB_NACOS_GROUP` / `DBHUB_NACOS_DATA_ID` | 可选；启用后从 Nacos 读取连接配置，Nacos 值优先于环境变量。namespace/group/data-id 建议 `dbhub` / `DEFAULT_GROUP` / `dbhub.properties` |
| `DBHUB_NACOS_USERNAME` / `DBHUB_NACOS_PASSWORD` | 启用鉴权时必填；使用只读账号，存放在运行 Secret |
| `DBHUB_NACOS_POLL_SECONDS` / `DBHUB_NACOS_TIMEOUT_MS` / `DBHUB_NACOS_REQUIRED` | 轮询 5–3600 秒（默认 15）、请求超时 200–60000 ms（默认 3000）、首次失败是否回退环境变量（默认 true） |
| `DBHUB_AUDIT_DIR` | 镜像默认 `/var/lib/dbhub/audit`，必须挂载持久卷、UID/GID 65532、目录权限 0700；Compose 已配置 `backend-audit` 命名卷 |
| `DBHUB_AUDIT_MAX_PENDING` | 默认10000，允许1–100000；默认记录约312.5MiB并另留目录/替换空间，队列满则拒绝新的审计操作 |
| `META_DB_MAX_CONNS` | 默认 10；所有者池和受限运行池各有此预算，每实例最多合计 20 个常驻池连接，另计目标数据库连接和运维连接 |
| `GOMAXPROCS` | 默认 4，不等同于容器 CPU 硬限额 |
| `JWT_ACCESS_TTL_MINUTES` / `JWT_REFRESH_TTL_HOURS` | 默认 15 分钟 / 168 小时 |
| `CORS_ALLOWED_ORIGINS` | 同源部署可留空；有跨域客户端时填写实际 HTTPS Origin，逗号分隔 |
| `DBHUB_TARGET_ALLOWLIST` | 必填，逗号分隔的 `host:port` 或 CIDR，例如 `inventory.example.com:5432,192.0.2.0/24`。匹配规则见[数据接入与执行契约](../架构设计/数据接入与执行契约.md#1-数据源身份与能力) |
| `DBHUB_LOGIN_MAX_ATTEMPTS` / `DBHUB_LOGIN_IP_MAX_ATTEMPTS` | 默认每个账号 10 次、每个来源 IP 60 次登录尝试，同一固定窗口内计数；Redis 原子共享，限流返回 429 和 `Retry-After` |
| `DBHUB_LOGIN_WINDOW_SECONDS` | 默认 300，范围 10–3600 秒；账号/IP 次数须为正数。超额请求不延长窗口 |
| `DBHUB_TRUSTED_PROXY_CIDRS` | 可选，可信代理 CIDR 逗号列表。默认按 TCP 对端计 IP；仅对可信代理链从右到左解析 X-Forwarded-For。部署时配置实际 Nginx/HTTPS 网关网段，按真实用户容量调整共享出口预算 |
| `DBHUB_AI_BASE_URL` / `DBHUB_AI_MODEL` / `DBHUB_AI_API_KEY` | 可选；模型稍后配置，不影响基础 SQL 工作台 |

```sh
docker compose --env-file /secure/dbhub.production.env -f docker-compose.prod.yaml config --quiet
docker compose --env-file /secure/dbhub.production.env -f docker-compose.prod.yaml up -d --wait --wait-timeout 120
docker compose --env-file /secure/dbhub.production.env -f docker-compose.prod.yaml ps
```

前端等待后端健康后启动。再通过实际 HTTPS 域名检查登录、真实 SELECT、权限与执行回执；检查管理员指标 `GET /api/v1/metrics/query`，确认回执存储可读。指标协议见[API规范](../接口规范/API接口规范.md)，指标只表达实际采集值，不构成性能验收门槛。

### Nacos 配置源（可选）

启用后，后端启动与运行期从 Nacos 读取 `DATABASE_URL`、`REDIS_URL`，**Nacos 中的键优先于同名环境变量**；Nacos 未提供的键才回退 env。Nacos 配置内容为 properties 格式，只识别上述两个键，其他键会被忽略。

- 首次读取失败：`DBHUB_NACOS_REQUIRED=true`（默认）时拒绝启动；设为 `false` 时回退 env 并记录 WARN，仅建议在接入窗口使用。
- 热更新：默认每 15 秒轮询一次。检测到内容变化后，先校验新 `DATABASE_URL` 的目标库 `schema_migrations` 版本与二进制内置迁移一致、新 `REDIS_URL` 可连通；校验通过后记录脱敏日志并优雅退出（退出码 75），由 systemd `Restart=on-failure` 或容器重启策略自动拉起生效。校验失败保持当前配置并记录 ERROR。
- 安全：Nacos 配置是明文存储，DSN 口令会落在 Nacos。必须使用独立 namespace 与只读账号（ACL 仅该 namespace），应用日志不输出配置值；控制台不得暴露公网。
- 运维注意：优先值改变后，`dbhub-runtime` Secret 中的同名 DSN 会被忽略；需要应急回退时设置 `DBHUB_NACOS_ENABLED=false` 并重启。

## 4. 迁移与备份

后端在监听 HTTP 前执行 `internal/db/migrations`，通过 `schema_migrations` 记录版本，同版本重启不重复执行。迁移范围以[当前迁移目录](../../backend/internal/db/migrations/)和实际schema_migrations为准，包含工作空间RLS、内容版本、任务及后续权限治理等增量，不将历史迁移数量作为当前恢复标准。首次迁移和索引建立时间受现有数据规模影响，应在发布前对脱敏副本验证。

启动元数据库身份须拥有迁移对象，能 `CREATE ROLE` 并授予当前 Schema 权限。应用创建独立随机登录角色作为受限运行连接，普通业务读取执行 RLS；所有者连接保留给登录、受控成员管理、迁移及恢复收尾。元数据库和中间代理须允许动态运行身份认证。正常停止会回收本进程身份，数据库不可用或强杀时可能遗留，运维应核对确切角色及活动连接后清理。托管 PostgreSQL 的授权能力和认证方式必须在部署前验证。

升级前记录旧镜像摘要、配置版本与迁移版本，停止发起新的 SQL，等待活动任务排空，并对元数据库做一致性备份。示例使用运维端已配置的 libpq service 和受控凭据文件，避免在命令参数中写入密码：

```sh
umask 077
./scripts/ops/backup-metadata.sh dbhub_meta_backup /secure/backups/dbhub-meta.dump
./scripts/ops/restore-metadata.sh dbhub_meta_restore_check /secure/backups/dbhub-meta.dump
psql --dbname=service=dbhub_meta_backup -X -f scripts/ops/verify-metadata.sql > /secure/backups/source-check.txt
psql --dbname=service=dbhub_meta_restore_check -X -f scripts/ops/verify-metadata.sql > /secure/backups/restore-check.txt
diff -u /secure/backups/source-check.txt /secure/backups/restore-check.txt
```

脚本依赖与服务端匹配的 `pg_dump`、`pg_restore`、`psql` 和受保护的 libpq service/pass 文件；口令不放进命令参数。备份文件权限为 0600，已有文件拒绝覆盖。备份排除所有权/ACL；恢复再次使用 `--no-owner --no-acl --single-transaction --exit-on-error`，拒绝已有用户表、视图或序列的目标库。应用首次启动会为当前进程重新授予受限运行权限。恢复指向新建独立空库，对账在应用启动前执行，避免引导更新或登录时间影响摘要。verify-metadata.sql提供20类基础对象对账，不能据此声称已覆盖后续MFA、导出、订阅、业务办理和全部IAM治理结构。当前恢复还须按实际迁移核对新增对象、收紧账、来源/配置代次、任务和密钥可解密性，再验证真实查询；未覆盖项如实保持待验收。

这些运维客户端也可运行在 PostgreSQL 工具容器中。恢复检查必须指向独立空库，验证迁移版本、用户、加密连接和回执数据。密钥管理系统要保留与备份对应的 `APP_SECRET_KEY`；数据库备份不包含该密钥，也不包含外部目标业务库的数据。审计待写卷须随实例保留，容器替换后复用该卷。每个副本独占一个卷；备份与迁移必须覆盖尚未落库的文件，不能在队列未排空时删除卷。具体恢复边界见[审计可靠写入](../架构设计/数据接入与执行契约.md#5-审计与恢复)。Redis 需要按会话保留策略备份；恢复元数据库不能恢复已经丢失的 Redis 登录会话。

可选docker-compose.ops.yaml使用独立私有备份卷。自动备份失败保留已有成功归档，成功校验后才按策略淘汰；备份目录私有，不提供浏览器下载。站内通知及故障/恢复告警规则见[内容契约](../架构设计/内容与交付契约.md#6-导出订阅和通知)。

| 留存及备份配置 | 当前规则 |
| --- | --- |
| DBHUB_AUDIT_RETENTION_DAYS | 默认0关闭，启用范围30–3650天 |
| DBHUB_HISTORY_RETENTION_DAYS | 默认0关闭，启用范围7–3650天 |
| DBHUB_READ_NOTIFICATION_RETENTION_DAYS | 默认90天，允许7–3650天 |
| DBHUB_BACKUP_EXPECTED_HOURS | 默认0关闭超期检查，启用范围1–168小时；不等于已启动自动备份 |

未知结果、防重键、不可变审批、内容版本和发布记录不由普通留存清理删除。清理及备份状态以实际配置和运行结果核对，不能把配置存在记作恢复验收通过。

## 5. 回滚步骤与边界

1. 停止新 SQL 请求并排空任务，保留旧镜像摘要、配置和备份。
2. 当前数据库结构与旧应用兼容时，将两个镜像变量改回之前通过验收的摘要，重新执行 `up -d --wait`，再验证登录、读取、回执及当前权限收紧。回退镜像须认识现行增量结构并执行撤权/冻结，不能退回会复活旧权的版本。不要自动执行反向DDL。
3. 结构不兼容时，停止写入，在维护窗口将升级前备份恢复到独立数据库，使用对应应用密钥、连接配置与兼容镜像切换。核对升级后的新增元数据，不能直接覆盖仍在使用的数据库。恢复旧备份前固定当前撤权、冻结、期限和作废凭证；在隔离恢复库核对并承接当前收紧后才能考虑切换，收紧不可读或无法承接则保持受限，不把旧备份中的旧权重新启用。
4. 后端重启会关闭目标连接、回滚未提交的活动事务；已自动提交的业务写入不会因应用回滚而撤销。取消、断网或进程终止后的 unknown 回执须核实目标数据库，不能自动重跑。

恢复验收覆盖实际版本的用户、空间、来源、治理、加密账号、内容版本、正式查询、任务、通知和审计重放防重。发布前保留已通过相同安全准入的回退镜像摘要，按实际升级前版本在独立数据副本验证兼容性；恢复点和恢复时间目标由生产部署方案确定，当前完成状态见[路线图](../项目管控/开发路线图与当前任务.md)。

## 6. 按已授权环境验证发布

默认在当前本地容器完成与改动相称的验证。发布前核对源码提交、镜像摘要、编排、迁移及环境配置；开发候选含未提交修改时还须记录完整工作副本指纹，不能只凭HEAD认定与部署一致，并验证登录、真实查询、回执、会话撤销、故障恢复、备份恢复和回退。容器健康、技术测试、产品验收与真实启用分别记录。

已有其他环境的辅助脚本见[scripts/cloud](../../scripts/cloud/README.md)，仅在明确使用该环境时按实际参数运行。它们的存在不授权迁移环境或自动执行历史release性能流程；阶段1已移出的性能测试与门槛不恢复。运行结果、日志和截图使用私有本地目录，不放入正式文档目录。

## 可选 JDBC 接入

可选JDBC按实际环境配置；生产使用单独的非 root 镜像和 `jdbc` profile。驱动、模板、实例工作流，`DBHUB_JDBC_URL`/`DBHUB_JDBC_TOKEN`、构建参数、权限和已验证范围见[数据接入与执行契约](../架构设计/数据接入与执行契约.md#1-数据源身份与能力)。生产仅运行预构建镜像，不在启动时下载驱动；是否可用须核对当前服务和能力范围。
