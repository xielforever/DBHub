2026-10-18。本批完成[设计范围](../项目管控/运维通知与数据源任务设计.md)，新增迁移 `0036_operations_inbox_source_tasks.sql`。

## 使用入口

| 入口 | 能力 |
| --- | --- |
| 页头「通知与待办」 | 未读计数、分页、单条及按高水位全部已读，实时待办进入对应审批和权限处理页面 |
| 数据源「巡检与采集任务」 | 连接检查、结构采集、阶段进度、取消、手动重试、定时计划及检查历史 |
| 数据目录「采集任务」 | 转入后台任务，带入选中的个人连接 |
| 系统设置「运行与备份」 | 平台管理员查看备份、留存配置、活动告警及审计待写状态 |

数据工作台 SQL 工具栏保持运行、格式化。采集对象为数据库、Schema、表、视图、字段及索引的结构快照；原同步 API 保留兼容，页面使用持久任务。

通知与原业务事务一起提交，回滚不产生通知，命令重试不重复通知。正式发布变化通知责任人及该版有效受众，受众链接进入正式查看页面。已有待办即时计算，已读不会完成审批；迁移不为历史事件补造通知。定时任务持续同一结果不重复提醒，失败状态变化及恢复会通知。运维告警仅发给平台管理员。首版使用站内通知。

## 任务与隔离

任务使用提交者自己的连接身份，固定工作空间、配置时间及成员版本，执行时重新验证；口令在执行时解密，任务记录不保存口令、SQL 或结果行。通知仅包含通用状态和受控资源标识，打开后由业务接口重新鉴权。切空间清空旧页面和计数，并取消旧请求。

同连接同类型最多一个活动任务；单用户 10 个、单空间 100 个、全局 200 个。数据库锁和租约合计限制 2 个执行槽位，每用户最多 200 个计划。任务最多执行 4 分钟，租约 5 分钟；过期/中断不自动重放。手动重试创建新任务，同一请求编号复用原记录，内容改变返回冲突。

排队任务立即取消，运行任务请求取消。发布前在同一事务校验任务状态及租约，快照发布和任务成功一起提交；已提交快照保留。失败或取消不会用不完整采集覆盖旧快照。

检查间隔为 5–10080 分钟，采集为 60–10080 分钟。保存后按间隔开始，停机不补跑积压时段；同类任务存在时跳过本轮。配置、授权或成员版本变化后，旧任务失效、旧计划暂停；重新保存或手动重试绑定当前配置。后台及原有手动连接检查都写入历史，旧配置检查单独标记，最近检查仍按配置和开始时间更新。

## 留存与告警

| 变量 | 默认 | 规则 |
| --- | --- | --- |
| `DBHUB_AUDIT_RETENTION_DAYS` | `0` | 0 关闭，启用为 30–3650 天 |
| `DBHUB_HISTORY_RETENTION_DAYS` | `0` | 0 关闭，启用为 7–3650 天，覆盖查询、检查及可清理的终态任务历史 |
| `DBHUB_READ_NOTIFICATION_RETENTION_DAYS` | `90` | 0 关闭，启用为 7–3650 天，创建及已读时间均超期才清理 |
| `DBHUB_BACKUP_EXPECTED_HOURS` | `0` | 0 关闭监测，启用为 1–168 小时，超过两倍预期成功间隔告警 |

留存每小时执行，每类最多 500 行，在一个事务内清理并记录计数，数据库锁防止并发重复维护。未知/中断任务、未知审计及仍被引用的父任务保留；连接和用户有未确认执行回执时保留对应查询历史。版本、审批、发布及执行回执不参与清理。

审计队列不可接收、积压达到 80% 或最旧事件超过 5 分钟，以及备份失败/超期、留存失败，会产生故障及恢复通知。元数据库不可写时记录结构化错误，恢复后重试检查；基础设施应监测就绪探针和备份服务健康状态。

## 自动备份

Cloud 的 `scripts/cloud/start.sh` 启用每日备份、14 天保留及 24 小时预期监测。新增 `metadata-backup` 服务以 UID 65532、只读根文件系统、无附加 capabilities 运行；私有 libpq 配置由已有开发绑定生成到独立只读配置卷，备份保存在独立卷。启动步骤可重复执行。

生产构建并启用可选编排：

```sh
docker build -t dbhub-backup:20261018 -f scripts/ops/Dockerfile scripts/ops
# 私有目录准备 pg_service.conf、pgpass 及需要的 CA。
# 目录 0700，配置及口令文件 0600，UID 65532 可读。
export DBHUB_BACKUP_IMAGE=dbhub-backup:20261018
export DBHUB_BACKUP_CONFIG_DIR=/secure/dbhub/libpq
export DBHUB_BACKUP_EXPECTED_HOURS=24
docker compose -f docker-compose.prod.yaml -f docker-compose.ops.yaml --profile operations up -d
```

默认 libpq 服务名 `dbhub`，可用 `DBHUB_BACKUP_SERVICE` 修改。地址、数据库、TLS 和账号保存在 `pg_service.conf`，口令在 `pgpass`。备份身份需要读取全部元数据（含 RLS 表），并写入运维状态和平台备份审计，使用受控运维账号及网络限制。

`DBHUB_BACKUP_INTERVAL_SECONDS` 默认 86400，失败重试 `DBHUB_BACKUP_RETRY_SECONDS` 默认 60，执行上限 `DBHUB_BACKUP_TIMEOUT_SECONDS` 默认 900，保留天数 `DBHUB_BACKUP_RETENTION_DAYS` 默认 14。完整备份、归档清单验证、SHA-256 和状态上报成功后才清理旧文件，至少保留两份完成备份，跳过其他文件及符号链接。失败保留已有备份及最近成功时间，当前失败单独记录。

镜像内 `/ops/restore-metadata.sh` 将归档恢复到独立空库，凭据通过服务文件读取。[对账 SQL](../../scripts/ops/verify-metadata.sql)核验 20 类核心对象，包括通知、任务、计划及检查历史。恢复需保留对应应用主密钥、驱动制品及尚未落库的审计持久卷；目标业务数据库另行备份。
