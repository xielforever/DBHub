## 连接测试如何判断

| 接口状态 | 界面提示 | 含义 |
| --- | --- | --- |
| `verified` | 版本已验证 | 产品、版本分支和补丁号与实测记录一致 |
| `branch_verified` | 同分支已验证，当前补丁待验证 | 同一产品、同一分支已有实测，当前补丁号不同 |
| `unverified` | 兼容性未验证 | 尚未验证的分支、预发布版、识别出的兼容产品或 Redis 部署模式 |
| `unknown` | 版本待确认 | 服务端版本无法可靠识别，或 Redis 账号无权读取 INFO |

版本判断来自服务端报告的身份信息：MySQL 使用 `VERSION()` 与 `@@version_comment`，PostgreSQL 使用 `version()`，Redis 使用 `INFO server`。识别到 MariaDB、TiDB、Percona、YugabyteDB、Valkey 等兼容产品时，不会按原生产品的测试结果标记为已验证。这不保证识别所有托管产品或隐藏身份信息的代理。

未验证版本仍可测试连接和使用已有功能；版本状态不会绕过 SQL 解析、安全校验或角色权限。Redis 能通过 PING 但 INFO 被 ACL 禁止时，测试连接返回 `ok=true` 与 `unknown`。认证或网络连接失败仍返回错误。

新建/编辑连接展示已验证分支；用户测试后显示当前服务端版本。已保存连接的卡片保留当前页面的最近一次测试结果，刷新或修改连接后清除，不把历史测试当作持续在线状态。表单变更会清除旧结果，测试途中修改目标后，较早的响应也不能覆盖新目标；同一连接测试进行中不重复发送请求。

接口详情见 [API 规范 4.5–4.6](../接口规范/API接口规范.md)。

## 验证覆盖与边界

每个版本使用独立真实目标容器，执行带 `-race -count=1` 的原生驱动测试和 HTTP 集成测试；不接受跳过、没有实际测试、版本不匹配或清理失败的结果。

- MySQL/PostgreSQL：建表、读写、实际影响行数、结果截断、错误 SQL、参数绑定、提交/回滚及独立连接可见性，表预览和字段/键/DDL 元数据；缺 WHERE 写入、只读角色和多语句防护。
- Redis：单节点 String、Hash、List、Set、ZSet 和 TTL，真实 INFO 概览；每个 Redis 版本额外验证无 INFO 权限的账号返回未知版本。Redis 6.2 不接受多个 INFO section 参数，现使用默认 INFO 获取概览所需信息。
- HTTP：登录、三种角色读取兼容矩阵和测试连接、查询/事务、代理转发、策略、工单及现有后端集成回归。匿名请求兼容矩阵返回 401。
- PostgreSQL 14–18 同时作为 HTTP 测试的元数据库，运行全部 19 个迁移及仓储读写。不同包顺序执行，避免测试表互相影响。

测试只证明这些基础路径在列出的具体镜像上通过：

- MySQL 5.7 本身没有 CTE、窗口函数等 MySQL 8 功能；工作台不会转换 SQL 或增加数据库缺失的语法。
- PostgreSQL 17/18 的新增语法仍受当前内置 AST 解析器与 SQL 安全规则约束，未覆盖所有新语法和扩展。
- Redis 仅验证单节点的五种基本类型；Cluster、Sentinel 和兼容产品尚未完成真实测试。
- 本轮为 Linux amd64、容器内直连、非 TLS 的测试。未穷举 TLS/SSH/代理与所有版本的组合、平台架构、字符集或插件，也不承诺该分支所有历史/未来补丁均已通过。

## 界面与回归结果

内嵌版本记录更新后，后端全量 `go test -race -p=4 ./...` 与 `go vet -p=4 ./...` 通过；前端 14 项执行状态测试、类型检查和构建通过。重启 Cloud 开发后端后执行版本界面的 7 项浏览器验收，页面错误为 0，桌面和 390×844 手机截图已检查。

[界面原始结果](../acceptance/datasource-version-ui-2026-10-16.json)覆盖三类真实数据源的版本显示、编辑后清除旧结果、迟到响应失效、未验证状态及手机表单。MariaDB 警示仅使用兼容信息契约样例，不能计作 MariaDB 产品实测。真实 PostgreSQL 截图在私有状态目录 `browser-artifacts/versions-desktop.png` 和 `versions-mobile.png`；警示样例单独保存为 `versions-unverified-*.png`。

本轮新增版本功能在 Cloud 开发栈验证；既有生产镜像的验收对应其报告记录的源码版本，尚未重建或发布包含本轮功能的生产镜像。

## 复现与更新记录

先按 [Cloud 开发环境](../../scripts/cloud/README.md) 启动基础数据库和后端。应用代码只在 Docker 内构建与测试，宿主 Python 只负责顺序编排容器。

```sh
# 完整 12 分支矩阵
python3 scripts/cloud/compatibility.py

# 单分支排查；不能用此结果更新完整支持清单
python3 scripts/cloud/compatibility.py --engine postgres --branch 18

# 环境问题修复后补跑失败项；要求后端 Go 实现未变
python3 scripts/cloud/compatibility.py --resume-from /私有报告路径/matrix.json

# 仅从完整有效报告更新内嵌实测补丁号，随后审核、提交
python3 scripts/cloud/compatibility.py --record-from /私有报告路径/matrix.json

# 版本提示浏览器验收
DBHUB_BROWSER_TEST_SCRIPT=/app/scripts/cloud/version_browser_test.py ./scripts/cloud/browser.sh
```

目标数据放在临时内存文件系统，无宿主数据库端口；凭据仅用于私有环境文件，结束后删除目标容器和凭据文件。默认删除本轮新拉取的镜像、保留之前已有镜像，`--keep-images` 可调整。VFS 环境应顺序执行，避免同时进行大量磁盘写入；不要在矩阵执行期间修改后端 Go 文件或重启后端容器。

首次运行有 11 项通过，PostgreSQL 18 因官方镜像更改数据目录约定而未启动。调整测试容器挂载后，在相同后端 Go 实现下补验 18.6，通过全部路径。最终报告记录了原报告摘要及复用项来源；原失败报告保留在私有状态目录。报告生成时实现尚未提交，所以 `source_revision` 为基线提交、`source_dirty=true`，`backend_go_sha256` 对应该次实测的 Go 源文件和模块清单。版本 JSON 在实测成功后导入，不属于协议实现指纹。

`.github/workflows/datasource-compatibility.yml` 提供手动 CI，顺序执行完整矩阵并上传 JSON 结果，不上传环境文件或测试日志。本轮实际执行的是 Cloud Docker 测试，尚未触发该 GitHub Actions 工作流。
