# Go 依赖安全修复与验收

本次修复基于 2026-10-19 对 `main` 的 `6cf5182` 扫描。原始扫描使用 Go 1.25.5；补查模块镜像路径后共命中 73 条不同公告，其中 38 条有静态调用路径、15 条仅命中已导入包、20 条仅命中模块。静态调用路径不等同于已在生产证明可以利用。

## 升级内容

| 组件 | 原实际版本 | 本次版本 |
| --- | --- | --- |

| pgx/v5 | 5.7.4 | 5.9.2 |

`go.mod` 最低工具链设为 Go 1.26.9。生产构建、Cloud 开发镜像和根目录开发配置同步更新；Go 镜像固定摘要。源码部署也必须使用对应的补丁版本，不能继续使用原 Go 1.25 工具链。

移除全部模块路径替换，以官方模块名解析依赖；重新生成并校验 `go.sum` 与 vendor。vendor 中 libpg_query 的 C 头文件仍由 `backend/scripts/vendor.sh` 从经过校验的模块缓存复制，保留 CGO 编译支持。大量旧 Unicode 表文件的删除来自上游 x/text 的新版本及其 Go 版本要求，未手工删改依赖实现以消除告警。

## 扫描结果与门禁

使用 Go 1.26.9、govulncheck v1.9.0、linux/amd64 对当前 vendor 执行源码扫描；漏洞库为 `https://vuln.go.dev`，库更新时间为 2026-10-08T22:31:09Z。已导入包与静态符号调用路径告警均为 0。

仍显示 **GO-2026-5932**：x/crypto 内未维护的 OpenPGP 包的模块级公告，没有公布修复版本。项目未导入或调用该包，不能把它计为项目已使用 OpenPGP，也不能据此宣称所有模块级公告为 0。本次没有屏蔽该公告、关闭数据库访问或更改扫描器的漏洞判定。

统一入口：

```sh
./scripts/cloud/dev.sh run --rm --no-deps backend sh scripts/vulncheck.sh
```

脚本固定 govulncheck 版本，检查模块路径替换并使用文本模式 `-scan=package ./...`。命中已导入包、依赖解析失败或漏洞库访问失败均返回非零。`--profile full`、`--profile release` 及生产准入 CI 已包含此步骤；smoke 明确记录未执行 Go 漏洞扫描。仅模块存在、未导入对应包的公告仍显示在日志中。

原始 JSON 扫描可能在包含 finding 时返回 0，不能只看退出码。本次另用旧版本的归一化依赖重跑同一包级命令，实际返回 3，验证门禁能拒绝存在漏洞的已导入依赖。

额外故障验证确认模块路径替换被入口拒绝，无法访问的漏洞库也返回非零。后者通过扫描器显式 `-db` 参数指向容器内的关闭端口验证；扫描器不支持用 `GOVULNDB` 环境变量切换数据库，不能把设置该变量后的成功运行当作故障验证。

Cloud 网络需要允许 `vuln.go.dev`，保存配置后确认当前运行策略已生效，再扫描。保留平台代理、CA 和模块校验。访问公网漏洞库不需要配置 Tailscale。

## 回归与部署验收

新增 `TestMetadataDollarQuotedParametersRemainData`，通过实际元数据连接池的 simple protocol 检查普通字符串、`$$...$$`、`$body$...$body$` 中的 `$1` 与真实绑定参数相互隔离。输入含有关闭美元引用和 SQL 片段的无破坏性探针；查询必须保留原字面量和参数值。旧 pgx 的两个美元引用用例失败，5.9.2 的三个用例均通过。

后端全量竞态测试和 go vet 通过，共 388 个通过事件（含子测试）、17 个测试包。Go/C/SQL/汇编源码及依赖元数据在验证前后逐文件比较一致。仅跳过专用子进程入口、独立版本矩阵和 openGauss 外部夹具；这些跳过不代表本次完成了完整版本矩阵或商业 GaussDB 验收。回归入口自测 9 项通过。

生产镜像、源码部署包与生产浏览器的最终结果记录在 [机器可读验收记录](../acceptance/dependency-security-2026-10-19.json)。历史的 2026-10-18 安全验收和容量基线保留其原始版本，不改写成新工具链的测试结果。

最终生产镜像中的实际二进制再次扫描，可达告警为 0；6 项生产浏览器安全检查通过，覆盖独立审批、完整 SQL 审阅、执行一次、提示 HTML 隔离、删除时保留他人行策略与 Cookie CSRF。源码部署包构建及工作流 actionlint 检查通过。

PostgreSQL 业务数据源的 5 个分支均通过竞态、真实 SQL/事务、HTTP 版本检查、连接可靠性与采集故障/取消回归：14.24、15.19、16.15、17.11、18.6。元库为 16.15，运行工具链为 Go 1.26.9，各分支无跳过且临时资源均已清理。此次没有重跑完整 MySQL/Redis 版本矩阵，也没有用部分报告改写原完整版本记录。

兼容矩阵的 HTTP 夹具将元数据库固定在 PostgreSQL 16，使用独立连接在实际业务目标上建表、采集、加锁与清理。业务数据源的 PostgreSQL 14–18 范围不代表元数据库也支持该范围；目标版本不得代替元库来执行应用迁移。报告同时记录 Go 工具链和元库版本，防止混淆两种验收对象。

本次范围为 Go 工具链及依赖修复。JDBC/JRE、操作系统镜像、实际生产网络/TLS、旧库恢复、完整数据源版本矩阵和真实业务负载仍按各自的发布验收执行。
