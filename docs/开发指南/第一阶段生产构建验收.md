## 2. 发现并修复的交付问题

- 原根 Compose 运行开发容器，缺少可直接使用的生产编排。本轮增加独立生产配置，要求指定镜像、应用密钥、管理员密码、元数据库和认证会话服务。
- 前端原 Dockerfile 通过多层转义的 `printf` 生成 Nginx 配置，且依赖安装失败会回退到 `npm install`。现改为独立配置文件和严格 `npm ci`，使用可选 Cloud CA 挂载完成真实构建。
- API 代理明确支持较长查询，传递客户端取消，不自动重放写请求，并动态解析后端地址，支持容器更换。
- 增加生产镜像健康检查。实际验收发现 BusyBox wget 会使用环境 HTTP 代理，导致本机探测收到 403；已让该检查直接访问固定的本机地址。后端探测成功返回 0，错误端口返回 1。
- Cloud VFS 存储在同时创建隔离数据库时耗尽持久盘。已移除本轮失败的空验收容器/卷、清理可再生构建缓存，将验收数据库数据放到临时构建盘后重新验证成功。开发服务健康检查通过。

## 4. 后端更换与持久化核实

[3 项原始结果](../acceptance/phase1-production-replacement-2026-10-16.json) 全部通过。准备一次受控写入后，停止并删除验收后端，临时占用旧地址，再启动同一生产镜像：后端地址从 `172.19.0.5` 变为 `172.19.0.7`，前端容器未重启，代理恢复访问。

原认证会话仍能访问，已成功回执可读取；重放同编号同内容得到 409/duplicate，同编号不同内容得到 409/conflict，实际 SQL 次数未增加。目标行的计数仍为 1。核实后删除测试表、撤销测试会话，删除私有临时会话状态文件。

这验证的是本地同一元数据库中、特定请求编号的持久化防重。目标库提交与元数据库回执并非分布式原子事务；对任意外部写入仍不承诺通用 exactly-once。
