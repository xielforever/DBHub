# SQL 工作台单实例容量基线（2026-10-16）

## 结论

正式基线 27 个阶段全部有效，阶段内共 43013 个执行 API 请求；其中常规读取 42878 次，全部 HTTP 200，返回数据逐行校验通过。过载、执行超时、客户端取消和真实 30 秒排队超时均符合预期，采样错误为 0，临时表、连接、账号及会话已清理。

第一阶段继续采用全局 8、每用户 2 个执行槽位，执行与等待合计全局 100、每用户 10 个任务，排队上限 30 秒。提高客户端并发至 32 后，四种读取负载相对 16 并发的吞吐变化均在约 ±3% 内，成功 P95 却升至约 1.7–2.0 倍。此次结果不支持继续扩大执行并发，也没有提供引入 Redis 查询缓存的依据。

这是一次短时、预热合成数据的开发环境基线，不能据此承诺生产容量或 SLO。下一次容量验证应使用脱敏的真实 SQL 与数据分布，加入锁竞争、写入、较大结果和至少 30 分钟混合负载；若仍观察到元数据库等待，再剖析连接池与执行链路。

## 测量方法

使用四个隔离的临时 developer 用户，每种数据库各建一张 10000 行表。每种负载先预热 8 次；随后测试 1、4、8、16、32 客户端并发，每阶段发压 5 秒。一个客户端收到响应并校验后才发下一次，无思考时间；记录请求开始至收到完整响应的延迟。

`point` 为参数化主键单行读取；`range100` 为参数化主键范围、排序后返回 100 行。所有返回的 ID、数值与标签均核对，不使用模拟结果。RPS 采用完整阶段用时，包含尾部请求排空和结束采样，略低于只按 5 秒发压窗口计算的数值。

成功延迟与 429 延迟分开统计，P50/P95/P99 采用客户端样本的 nearest-rank。排队均值来自本阶段服务端直方图累计和差值；`queue_wait_p95_upper_ms` 仅为桶上界，原始 JSON 保留该近似值。本报告表中列出精确客户端成功 P95，不混用这两个口径。

以 500ms 间隔观测进程、队列、元数据库连接池及目标数据库连接。阶段边界要求无执行中请求，并对请求数、成功/拒绝数、实际 SQL 次数进行对账；故障探测另外验证超时、取消及排队拒绝计数。

## 过载与异常探测

| 数据库 | 场景 | 观测结果 |
| --- | --- | --- |
| PostgreSQL | 64 请求同时执行 0.3 秒慢查询 | 40 成功、24 个 429；SQL 实际执行 40 次；429 P95 40.7ms |
| MySQL | 同上 | 40 成功、24 个 429；SQL 实际执行 40 次；429 P95 34.9ms |
| PostgreSQL | 2 秒慢查询，执行超时 1 秒 | 约 1.02 秒完成探测，HTTP 400、回执 unknown；超时 +1、取消 +0 |
| MySQL | 同上 | 约 1.01 秒完成探测，HTTP 400、回执 unknown；超时 +1、取消 +0 |
| PostgreSQL | SQL 已开始后取消 HTTP | 客户端无响应；服务端取消 +1、超时 +0，实际执行 +1 |
| MySQL | 同上 | 客户端无响应；服务端取消 +1、超时 +0，实际执行 +1 |
| PostgreSQL | 同用户两个慢查询占满槽位，第三个等待 | 第三个约 30.007 秒后返回 429/rejected，未执行；排队超时 +1，取消两个占用者后取消 +2、实际执行共 +2 |

过载探测采用四个用户；40 个任务被接纳对应每用户 10 个任务上限，不代表已经触发全局 100 个任务上限。全局执行槽位累计峰值未超过 8，所有阶段结束均验证请求与队列排空。故障场景没有成功响应时，成功延迟样本数为 0，不能将其解释成“成功 P95 为 0”。原始 JSON 的 HTTP 状态 `0` 表示客户端取消后没有收到响应，不是服务器返回的状态码。

执行超时或取消仍按现有契约保留 unknown 回执，未自动认定写入已回滚，也未自动重试。本次故障注入使用受控读取，不能据此推断所有数据库写入的最终提交状态。
