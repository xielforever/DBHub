# 开发指南

本文合并本地环境、编码、Git和文档维护要求；[当前路线图](项目管控/开发路线图与当前任务.md)决定任务范围，[业务执行契约](架构设计/数据接入与执行契约.md)和[内容契约](架构设计/内容与交付契约.md)决定功能及安全边界。

## 1 本地环境

默认使用指定检出和现有本地容器，不自动迁移云环境。操作前确认路径、分支、Git状态、现有Compose项目、配置和环境文件，沿用原来的项目名、-f和--env-file参数，保留已有修改、服务与数据卷。

工具与依赖版本以[前端清单](../frontend/package.json)、[Go清单](../backend/go.mod)、锁文件及Dockerfile为准，不为宿主环境擅自降级。根[开发编排](../docker-compose.yaml)与[生产编排](../docker-compose.prod.yaml)分开；不把生产运维脚本作为普通开发默认入口。CGO及SQL解析器头文件按现有构建/vendor流程保留。

环境文件使用受控本地值，不输出完整配置、真实凭据或连接串；开发样例不得带入生产。复制文件不代表Compose自动采用，须核对实际命令参数。上游检出、容器状态和依赖未确认前，不另起一套环境。

## 2 开发与就绪

### 本地应用连接远端基础服务

前后端均在本地开发容器运行，前端仍经同源 `/api` 访问本地后端。仅PostgreSQL元数据库与Redis改接用户授权的现有Tailscale服务，不通过这项配置新建远端容器或修改服务器配置。

真实地址和凭据保存在被忽略的根 `.env.local` 中：`DBHUB_METADATA_URL`、`DBHUB_REDIS_URL`、`DBHUB_TARGET_ALLOWLIST`。字段格式见[配置示例](../deploy/local/remote-services.env.example)。PostgreSQL使用TLS `verify-full`，连接主机名匹配证书SAN；通过 `DBHUB_INFRA_HOSTNAME`/`DBHUB_INFRA_ADDRESS` 将证书主机名映射到Tailscale地址，并把 `DBHUB_INFRA_CA_FILE` 指向经可信渠道核对的公开证书文件，只读挂载到后端供验证使用。不得自动信任未经核实的证书、关闭证书验证或修改远端TLS配置。Redis使用分配给知数的逻辑库与既有dbhub命名空间，经Tailscale加密隧道访问，不能清空共享Redis或修改其他项目配置。

沿用既有Compose项目、配置文件和依赖卷，追加[基础服务连接覆盖文件](../deploy/local/remote-services.override.yaml)，仅重建本地后端/前端。在WSL仓库目录执行：

```sh
docker compose --project-name dbhub-local --env-file .env.local -f .dbhub/local/compose.yaml -f deploy/local/remote-services.override.yaml up -d --no-deps backend frontend
```

该覆盖文件移除后端对本地PostgreSQL/Redis的启动依赖，并将它们纳入local-infrastructure profile。覆盖文件使用 Compose 的 `!reset`。重建前可用同一组项目名、配置文件和环境文件参数执行 `config --quiet`，检查配置解析且不输出展开值。证书使用只读文件挂载并禁用自动创建源路径，填写运行 Compose 一侧可读的现有文件路径。已有本地数据卷必须保留；仅在迁移验证完成后停止旧基础服务，不删除卷。配置变化使用up重建，普通restart不会重新注入环境变量。后续维护继续使用相同覆盖文件，远端不可达时不得自动回退。

切换数据库之前须取得建库/迁移授权，备份源数据库、停写并迁移到空目标，按表名核对行数和schema_migrations；保留应用加密密钥，避免已有数据源凭据无法解密。后端启动会执行迁移，不能把启动视为只读连接测试。`DBHUB_MIGRATION_TIMEOUT_SECONDS` 控制整个启动迁移/运行账号初始化时限，默认30秒，允许1–600秒；远端开发可配置180秒，不更改业务查询超时。现有运行账号隔离机制要求元数据库所有者具备CREATEROLE（无需SUPERUSER/CREATEDB/BYPASSRLS），每次启动创建独立受限运行账号并显式授予当前库CONNECT，支持已撤销PUBLIC连接权的数据库；业务查询继续使用受限账号与原权限校验。测试库使用另一个独立账号。

`DBHUB_READINESS_TIMEOUT_SECONDS` 控制依赖就绪探针总时限，默认2秒、范围1–60；`DBHUB_REDIS_PROBE_TIMEOUT_MS` 默认500毫秒、范围1–10000。高延迟VPN开发环境可分别设为10秒/3000毫秒。远端覆盖文件为 Compose 健康检查保留65秒上限，以覆盖服务端最大就绪预算、探针客户端1秒缓冲和命令调度开销。`DBHUB_LOGIN_REDIS_TIMEOUT_MS` 控制登录限流Redis单次I/O，默认500毫秒、范围1–10000；脚本首次加载的总预算为其两倍，远端开发可设3000毫秒。限流次数、窗口、原子脚本及Redis故障时拒绝登录的行为保持不变；这些配置不将失败伪装为健康，也不取消原业务超时。

`DBHUB_CONNECTION_CHECK_PERSIST_TIMEOUT_SECONDS` 控制保存连接检查回执的时限，默认3秒、范围1–60，远端开发可设15秒；目标数据库握手仍按连接本身的超时控制。`VITE_CONNECTION_TEST_TIMEOUT_MS` 统一控制普通新建、已保存连接和数据源目录个人连接这三个测试入口等待完整请求的时间，默认25000毫秒，允许25000–300000，远端开发可设90000。保存失败仍报告失败，不丢弃检查记录或绕过工作空间事务。该配置不改变新增绑定等写请求的超时，不自动重放请求。

`VITE_DATABASE_LIST_TIMEOUT_MS` 控制查询目标选择器读取数据库列表的等待时间，包括选源和确认目标时的权限复验。接受 15000–300000 毫秒的整数。远端覆盖默认设为 90000 毫秒，通用编排沿用应用请求默认值 15000 毫秒。变更后重建本地前端容器，使 Vite 读入新值。

`VITE_IAM_EFFECTIVE_TIMEOUT_MS` 控制读取当前工作空间有效权限和确认显式工作空间时的客户端等待时间。接受 15000–300000 毫秒的整数，远端开发覆盖默认设为 45000 毫秒，通用编排沿用请求默认的 15000 毫秒。权限读取失败仍撤下旧权限，身份或工作空间变化仍作废在途结果。配置变更后用原编排重建前端容器。

验证本地 `/api/health`、`/api/ready`、登录和工作空间读取，并使用独立测试库验证连接及查询。逻辑迁移须恢复原函数的PUBLIC执行权限与撤销状态，不沿用旧进程临时运行账号。回退须考虑远端切换后新写入，不能直接使用过期本地副本覆盖远端数据。

使用已保存的测试源验收时，先在对应工作空间调用 `POST /api/v1/workspaces/{workspace_id}/connections/{id}/test`，读回 `ok=true` 和 `recorded=true`。用同一连接执行获准的只读查询，核对列和样本行，并从 `GET /api/v1/workspaces/{workspace_id}/query/executions/{request_id}` 读回同一请求的终态。页面验收沿用这个连接和测试库，从「我的连接」打开工作台并核对显示结果。

本机完整备份的核验同时记录最新定时备份和实际参加恢复演练的归档。恢复回执包含归档名称及 `SHA256SUMS` 的 SHA-256。复核时重新验证两份归档的文件校验及恢复回执的指纹；归档缺失、发生变化或旧回执缺指纹时，应补做隔离演练。继续已有演练也须使用同一归档内容。最新备份完整与对应归档已恢复分别记载，定时轮转后仍可复核留存中的已演练归档。该流程针对本机完整归档，发布验收另需核对目标构建、当前工作副本及配置、数据和回退证据。

根目录默认编排可按需使用以下命令；已有编排不同则调整参数。文档任务不启动应用、不安装项目依赖或重建环境。

```sh
docker compose ps
docker compose up -d
docker compose exec -T frontend npm ci
docker compose exec -T frontend npm run build
docker compose exec -T backend go vet -mod=vendor ./...
docker compose exec -T backend go build -mod=vendor ./...
```

首次使用或锁文件变化时核对前端实际依赖卷；宿主node_modules存在不能证明容器就绪。up -d只表示启动请求，须查看日志、前端和/api/ready，再按功能检查登录/取数。只读检查与文档维护无需启动服务。

## 3 编码约定

- 文档及说明用简体中文，代码标识符用英文。按现有目录、命名和组件复用，不为架构示例新建无用途层级。
- Vue使用Composition API、script setup lang=ts和严格类型，按script、template、style组织；遵循所在目录的现有命名，不无关重命名。Props/Emits及Store依赖按本次改动说明。
- 复用API封装、类型、用户/空间状态和图表组件。界面覆盖加载、空数据、失败、无权限、键盘及响应式，主题令牌见[UI规范](界面设计/UI设计规范.md)。
- Go变更运行gofmt，导出符号和复杂逻辑补充必要注释；错误处理或携带上下文向上返回，不静默吞没。
- SQL值参数化，动态标识符验证或安全引用；事务检查开始、提交与回滚错误，不能复制忽略错误的示例。
- 升级新增[内嵌迁移](../backend/internal/db/migrations/)，不改已应用历史迁移。权限在后端及执行边界生效，不仅隐藏菜单。
- 依赖有明确用途并同步清单/锁文件，vendor按[现有脚本](../backend/scripts/vendor.sh)更新，不手工改第三方代码。

## 4 验证

按改动风险选择已有脚本和受影响包，不机械重跑全部检查。前端脚本以清单为准，可用test:query、test:report、test:dashboard、test:automation；后端可用go test -mod=vendor并按包或-run筛选。

集成测试使用隔离数据库/服务；TEST_POSTGRES_DSN、TEST_METADATA_DSN、TEST_REDIS_URL等缺失导致跳过时如实说明，不把跳过算覆盖，不重置现有业务库。用户界面变更按任务验证真实操作；测试通过、产品逐项验收和真实启用分别记录。已移除的性能任务不恢复。

文档只核对规则、链接、表格和图源；图源变化再做解析/渲染检查。交付区分通过、失败、跳过与未执行，并说明未执行原因。

## 5 Git与文档

使用当前分支和工作区，非任务所需不自动建分支、切换、提交、推送或合并。用户要求新分支且未指定名称时采用codex/前缀。用户要求提交时按Conventional Commits，聚焦本次内容，排除秘密、运行产物和无关修改；不使用全仓库重置/清理处理文档问题。

只更新受影响的接口、结构、UI或运行说明。已有契约足够明确的修复直接实施并验证，不另起RFC、评审、定稿或日期计划。阶段/待办在路线图，模块范围在模块总览，规则在对应契约，字段在API/数据库/UI规范维护，其他地方引用。

正式文档约12份，使用稳定文件名。纯过程材料不因“已定稿”继续进入Git；有效规则先承接，已合并旧稿与跳转壳删除。只保留未完成验收、未关闭问题或无法重建且仍需追溯的最小本地资料，统一放 .local-docs 并忽略。
