# 报表口径与权限变更契约

> 2026-10-18 · 已实现的报表契约及受众变更规则。对应[仪表盘第一阶段设计](../项目管控/仪表盘第一阶段设计.md)；实际接口、验证范围与部署要求见[实施与验收](../开发指南/仪表盘第一阶段实施与验收.md)。

## 1. 获批的报表契约

### 1.1 字段与来源

报表定义增加 `data_contract`，随不可变内容版本送审；批准摘要包含其规范化哈希。每个工作空间内的逻辑报表 ID 稳定，仪表盘冻结该 ID 和预期契约哈希，运行时跟随契约兼容的当前正式发布。

提交者只声明业务与结果字段。执行边界在审批选择账号后由服务端与工作空间一起补齐到批准清单，形成最终契约哈希；不能回写已冻结内容版本。仪表盘只接受拥有最终获批契约的正式报表。

| 字段 | 规则 |
| --- | --- |
| `semantic_key`、`meaning` | 稳定业务指标标识及说明，例如“可售库存按含税采购成本计价”；变更含义必须视为不兼容 |
| `result_schema` | 列名、顺序、逻辑类型、NULL 规则；维度和指标映射、图表类型；包含水位列映射，不能新增未声明的结果字段 |
| `unit`、`currency` | 明确倍率和 ISO 币种，例如 `CNY_10000`、`CNY`；计数可用 `item_count` 且币种为空，不允许默认猜测 |
| `timezone` | IANA 名称，例如 `Asia/Shanghai`，控制业务日期与水位解释 |
| `scope_key`、`scope_description` | 本组织内统计范围标识与说明，例如三个指定仓库、是否包含冻结/在途库存；由报表审批人审阅 |
| `time_window` | 当前时点、自然日、固定期间或滚动窗口及边界；七日趋势与当前余额不能因同用“万元”就认为时间窗相同 |
| `comparison_key` | 可比较的业务指标族；仅在范围、单位、币种、时区和窗口语义一致时用于比较组，不要求图表类型相同 |
| `execution_boundary` | 服务端补齐的数据源修订、数据库、独立执行账号身份；不包含密码，普通查看 DTO 不暴露内部目标 |
| `freshness` | `watermark_column/unverified`、水位列名、最大数据年龄、允许的未来时钟偏差；不得以客户端传值冒充 |

兼容哈希覆盖业务含义、结构、维度/指标/图形、单位、币种、范围、窗口、时区、执行身份和时效规则；不含密码、SQL 正文、受众、报表显示名称、内容版本号、发布事件号或查询完成时间。哈希由服务端计算，客户端不能直接指定。

### 1.2 兼容与不兼容

报表提交者声明与上一正式契约的关系，另一位合格审批人确认 SQL、返回样本和业务范围是否仍符合该契约。相同契约哈希只是必要条件，不能证明两条 SQL 语义等价；系统不自动把相同列名解释为相同口径。

同契约 SQL 修复、同口径回滚或仅扩大/收紧受众不使仪表盘引用永久失效。调整币种、倍率、范围、窗口、结果字段、数据源修订、数据库或执行账号身份应产生新契约；仪表盘需要通过新草稿重新确认。仅轮换同一账号密码不改变契约。

兼容声明、批准者、批准契约及反向依赖影响写入审计。对不兼容变更，报表发布者确认将阻断的当前看板/卡片数量；报表安全下线、撤权和账号停用不因看板依赖被禁止。

### 1.3 时效和结果验证

`watermark_column` 模式由获批 SQL 返回业务截止时间。服务器检查 RFC3339/明确时区时间、同次结果中非空水位一致性，拒绝超出批准未来偏差的值；默认最多允许未来 60 秒。水位缺失或零行时标为未知，不用数据库 NOW() 或执行时间偷偷替代业务水位，也不把 NULL/无行伪装成零。

水位列用于控制元数据，图表仍按原维度/指标映射展示；结果详情保留准确原始字段。历史趋势每行可有不同业务日期，但需另有一致的源处理水位，不能把最早趋势日期当作当前数据截止时间。

`unverified` 明确表示不能验证时效。它可被报表正常使用，加入看板时必须通过“允许未知时效”的显式审批和组织策略；页面始终提示未知。查询完成时间、页面结果年龄、业务数据年龄分别记录。

比较组校验所选主指标的 `comparison_key`、范围、单位、币种、时区和窗口，执行后比较水位差。总额和仓库分布可以同组；七日趋势不因此被视作同一当前余额窗口。该校验只证明声明口径可比较，不在浏览器求和或承诺数据库快照一致。

执行时验证结果结构与获批契约，并继承报表的数值保真、1000 行和强制只读约束；结构不符、字节超限、截断不得继续绘制假完整图表。时效阈值和结果保留时间可被工作空间策略收紧，不能放宽组织禁止未知时效等约束。

### 1.4 迁移

历史正式报表不自动生成“可信”口径或水位。保留其独立查看能力，提供补充契约并送审的入口；契约缺失时不能加入新正式仪表盘。原内容版本和批准摘要不原地改写，新契约通过新的报表版本生效。

## 2. 受众变更与访问申请

### 2.1 首期采用已有审批发布模式

现有批准清单把受众和报表内容一起冻结。首期不直接 UPDATE 已批准受众，也不把访问申请表当成权限表；通过“仅调整受众”提案复用审批、实际只读验证和显式发布。此流程需要新增维护入口，不能假装当前普通草稿接口已经支持。

“仅调整受众”提案由本工作空间资源负责人或管理员发起，服务端从当前正式版本复制 SQL、图表、契约、数据源和执行账号，只允许变更受众。无需借用离职作者的个人连接；任何 SQL/契约/账号修改均拒绝，须改走完整报表开发审批。

复制形成新的不可变内容版本与待审申请。继承的 SQL、契约和执行身份必须与基准正式发布摘要一致；验证/批准继续使用显式、受审计的报表审批预览能力，不能将审批预览权冒充普通报表查看授权。仪表盘审批仍要求拥有全部引用报表的普通查看权限。

审批人必须为有效组织管理员，不能是提案提交者、权限申请人或本次新增个人授权的受益人。新增组授权时同样识别审批人的直接受益，需另一位合格管理员处理。人员不足时返回明确阻断原因，允许资源负责人补齐其他合格审批人，不开放自动自审或平台管理员兜底读取。

仅变更受众会产生新的报表发布事件，但契约保持一致，跟随该报表的看板下一刷新继续工作。首期接受必要的发布次数；独立授权版本与内容版本的拆分留待后续专门迁移，不混用两套授权来源。

### 2.2 流程、竞态与终态

1. 申请明确目标用户/组、理由、期望范围、申请人和关联看板。普通用户只能申请本人权限；管理者申请群体授权也只限当前组织的拟发布受众和引用资源。
2. 服务端对未知/跨组织目标使用统一外部响应，只有确实属于本组织且可处理的目标创建内部申请。受限卡片的名称不因申请而泄漏，申请人只能看到自己的安全状态摘要。
3. 负责人受理后绑定“仅调整受众”提案，申请为 `processing`；批准后为 `approved_pending_release`。批准、处理人接单或发出通知都不等于授权成功。
4. 发布必须绑定基准 `report_publication_no`、批准摘要、关联申请当前状态和组版本。若期间已有其他发布，返回冲突；从最新受众生成新的提案并重新审批，不能把后来新增的授权覆盖掉，也不能在批准后暗中合并受众。
5. 发布生效后重新检查目标仍是有效成员且当前权限满足，才原子登记 `fulfilled` 并关联实际发布。多目标申请逐目标记录结果，不把部分成功误记为全部完成。
6. 拒绝需理由；申请人可撤回未完成申请；7 天到期、父资源归档或目标失效会终止申请。已经批准但未发布的关联变更必须被取消/过期门槛阻断，不能借旧批准继续授予该申请要求的新权限。
7. 已完成的申请撤回不是撤权。收回权限走单独受众收紧/组成员移除/成员停用流程，立即应用运行时检查，记录影响和审计。

同一报表的多份申请可以由处理人合并为一个明确的受众提案，批准摘要必须列明全部关联申请和最终受众。任何关联申请在发布前取消，整份批准不得继续原样发布，应生成新的提案；不允许悄悄删改批准清单。

受众收紧是独立管理操作，不能被“当前看板需要这些人”阻止；应提示影响并保留审批/紧急停用路径。紧急撤权可停用成员或下线报表，禁止为了绕审批而借他人连接执行。

报表权限申请完成后授予的是独立报表访问权，不局限于发起申请的看板；页面及审批明确展示该事实。看板自身受众变更也生成新的看板内容/审批版本，仍须通过必需报表覆盖门槛，不自动授予子报表权限。

### 2.3 拟新增接口和控制记录

以下路径省略 `/api/v1/workspaces/{workspace_id}`，所有请求校验组织、成员、操作权限、UUID 和版本。

| 接口 | 约束 |
| --- | --- |
| `POST /managed-reports/{id}/audience-changes` | 仅复制当前正式定义和执行身份；输入基准发布号、拟受众、关联申请及 UUID；禁止 SQL/连接覆盖 |
| `GET /access-requests/{id}` | 申请人或处理范围内管理员的裁剪视图，状态不能泄漏受限资源细节 |
| `POST /access-requests/{id}/assign` | 重分配组织内有效处理人，校验申请版本；处理人不因此获得数据权 |
| `POST /managed-dashboards/{id}/audience-changes` | 复制看板布局，明确受众变化并重新校验覆盖和审批人，不原地修改已批清单 |

申请在 `sys_access_requests` 中以 `target_user_id/target_group_id` 保存独立目标，并关联变更审批 ID；关系键包含工作空间。发布事务与申请终态必须一致提交，防止“已取消却被授予”或“已完成但未发布”。站内队列按资源负责人/合格管理员展示，不调用外部消息渠道。

## 3. 需要共同验收的边界

- SQL 修复与受众扩展在契约不变时不会批量停用看板；实际执行仍绑定当前正式发布及每轮版本。
- 仅调整受众不能替换 SQL、图表、契约、账号或数据源，也不要求恢复作者个人连接。
- 两个管理员并发批准不同受众提案，后发布者不能覆盖先前授权；冲突后必须重新生成提案。
- 批准未发布、申请取消/过期、发布失败、组被删除、成员停用均不能显示授权完成。
- 新增组成员只有在同组织、有效成员且两级授权都满足时可读取；删组和移除成员实时阻断后续交付。
- 当前数据权限在发送 SQL 和交付前重查；兼容声明不能跳过权限、账号代次、组织或字节预算。
